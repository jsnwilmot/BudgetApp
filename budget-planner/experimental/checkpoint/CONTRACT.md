# Stage 1 contract (frozen before implementation)

Synthetic-only, pure in-memory API. No application imports, storage, clock, random IDs, recurrence generation or activation. Not wired into production. Issue #14 and conditional design approval in #13; baseline 2825478. All amounts are canonical integer minor-unit **strings**, never JS money numbers. CAD/USD/EUR/GBP/AUD/NZD/CHF only; one currency per calculation. Dates are ISO calendar dates, interpreted as start-of-day in the explicit IANA zone (no UTC instant conversion of a bank posting).

`calculateCheckpoint({checkpoint, events, boundaryDecisions=[], representationPolicies=[], throughDate, legacyContext})` returns `{ok, diagnostics, ...}`. Blocking diagnostics yield **no balances or partial ledger**. legacyContext is opaque, never a financial input or mutated. Inputs retain IDs, modes, validation, notes, marker, original openings and cadence. Outputs are fresh values.

Checkpoint: `{id, date, timeZone, currency, originalAnchor, frequencyDays, verified:true, basis:'posted', evidenceRef, accounts:[{id,type:'chequing'|'savings',currency,openingMinor,verified:true,evidenceRef,active?,allowOverdraft?}], buckets:[{id,accountId,openingMinor,verified:true,evidenceRef}], unallocated:[{accountId,amountMinor}]}`. All savings accounts require explicit unallocated opening; reserved+unallocated must equal each bank opening. Inactive nonzero accounts participate. Negative savings/reserves forbidden; negative chequing requires explicit overdraft permission.

Event: `{id, origin:{kind:'scheduled'|'manual'|'adjustment',id,revision}, accountingDate, assignedDate, currency, amountMinor, kind, validated:boolean, settlement:'posted'|'forecast', movementId?, sequence, fromAccountId?,toAccountId?,bucketId?,toBucketId?}`. No inferred account or amount. Validated events must be posted; only these affect the validated track. Projected uses all eligible events once (posted or forecast), including validated events once, not validated plus forecast copies. Unknown/partial status blocks. sequence is an explicit nonnegative safe integer, unique within each accounting date after representation decisions; missing/ambiguous same-day ordering blocks rather than guessing by array/ID. Dates may be off-grid; assigned date is identity/grouping metadata, not settlement date. Recorded revision is mandatory; Stage 2 must enforce staleness externally.

Kinds: income credits toAccount; expense debits fromAccount; contribution debits chequing/credits savings and allocates to bucket on that savings account; withdrawal reverses those legs and releases bucket; allocation moves unallocated savings to a bucket (no bank leg); release returns bucket reserve to unallocated (no bank leg); reallocation moves between buckets on the same savings account (no bank leg). Direct savings expense with bucketId releases that reserve in the **same event**. No separate negative bank adjustment is invented. All event amounts positive; unsupported arbitrary corrections reject.

Fence: accountingDate<T excluded and preserved. If assignedDate>=T but accounted<T, an explicit already-in-opening decision is required. If assignedDate<T and accountingDate>=T, explicit carry-forward is required. An on/after-T event already covered by opening can be suppressed only by an explicit already-in-opening decision. Decisions `{eventId,revision,kind:'carry-forward'|'already-in-opening',evidenceRef}` are exact, unique, checked and consumed. Forecast/unknown settlement cannot be claimed already posted in opening. No partial carry amounts.

Identity: event IDs and (origin kind,id) unique. Same movementId claims or coincident contribution/withdrawal kind/date/amount/routing require explicit policies: `{eventIds:[...],decision:'distinct'|'representative',representativeId?,evidenceRef}`. Distinct is invalid for a shared movementId. Representative requires identical financial semantics, settlement/validation and accounting/assigned dates; expenses cannot be merged with contributions. All raw events remain intact; output records chosen/excluded identities. No heuristic deletion. Unused, conflicting, overlapping or stale decisions reject. Policy grouping is an exact in-memory representation assertion, not historical correction or certification.

Output: immutable-input result with opening, chronological event rows (bank/reserve/unallocated debit/credit legs and validated/projected snapshots), final snapshots, monthly accounting-date income/expense/contribution/withdrawal totals, and partial-cutover-month qualification. No checkpoint income. Aggregates derived only from per-account cash; buckets never added as assets. Overdrawn reserves, savings, unallocated funds or unapproved chequing overdraft block both tracks. throughDate>=T is mandatory; later events remain preserved and excluded from that view. No lifetime horizon generation.

`previewCheckpoint(input, reference)` adds exact differences against an independently supplied synthetic reference `{validated,projected}` in the same snapshot shape. Missing/different identities or malformed reference reject. It never accepts a real backup or baseline activation command. This is a typed JS contract with runtime validation; not an approved persisted schema.
