# Stage 2 integration proposal — not implemented or authorized

Stage 1 code is never imported by App, existing projection/report logic, IndexedDB, migrations, backup services or the offline backup CLI. It accepts only an explicit in-memory contract; it does not read JSON/files, generate recurrences, use a clock, or persist any record. Existing 25/22/2 history is context, not a source of inferred opening values. A synthetic caller may retain that context in `legacyContext`, which the engine never reads.

## Stage 1 API and independent evidence

See CONTRACT.md for field types and rejection rules. `calculateCheckpoint` returns fresh exact-string snapshots, per-event debit/credit legs, exclusions by identity, monthly totals by actual accounting date, and a partial-month qualifier. `previewCheckpoint` adds signed differences against a supplied synthetic ledger. No activation or source/account mapping command exists. An invalid event, opening, policy or intermediate balance blocks the whole result; there are no partial trusted totals. The first blocking diagnostic includes a code and exact input reference where applicable. Unlike the anonymized backup CLI, this API deliberately returns synthetic detailed ledgers and must **not** be exposed to private data/logging in Stage 1.

Independent hand ledger used in tests (minor units): opening C=200000, inactive C2=50000, S=300000, S2=10000. Tax=120000, Emergency=150000, Other(S2)=5000; unallocated S=30000/S2=5000. Salary +100000 to C; contribution 10000 C→S/Tax; withdrawal 60000 S/Tax→C; actual tax expense 60000 from C. Validated end: C=290000/C2=50000/S=250000/S2=10000, Tax=70000/Emergency=150000/Other=5000; cash=600000. An unvalidated future contribution 15000 changes only projected C=275000/S=265000/Tax=85000. Original history remains unchanged. Direct savings expense has one savings debit and reserve release in one atomic event; release/reallocation do not move bank assets. Reports include the off-grid Jan 2 expense in January. Checkpoint opening creates no income or spending.

Full amounts are integer strings and parsed with BigInt. No implicit number-to-string conversion or rounding. Only the declared two-decimal currency set is supported. Amounts are minor units, not display decimals. Explicit event sequence orders same-day transactions; no inference of bank settlement order. Both validated and projected paths must remain fundable at every step; an unvalidated inflow cannot fund a validated expense. Insufficient reserves/unallocated savings, unsupported negatives or unknown/partial settlement block. Nonnegative savings is the Stage 1 policy, not a universal bank constraint; overdraft support is explicit chequing-only.

Representation policy is evidence supplied by the synthetic caller, not evidence authentication. Conservative contribution/withdrawal coincidence checks can block two legitimate movements until `distinct` is supplied; representative decisions require matching financial semantics and settlement/validation status. Neutral internal account transfers move exact bank cash without touching reserve ownership or income/expense. Savings can transfer only unallocated funds; reserved funds require an explicit allocation release or funding withdrawal. Forecast versus posted differing claims require external reconciliation in Stage 2, not silent merging. Covered opening versus a forward same-movement claim blocks until the forward identity is explicitly accounted for. Cross-date economic duplication without a shared movement identity cannot be inferred: the owner must establish boundary membership/evidence. Partial settlements, FX, arbitrary bank corrections and cross-account bucket reallocations are unsupported. Source revision strings are retained, not checked against any database in Stage 1.

## Required Stage 2 adapter and stop gates

1. Separate owner/Architect authorization before using any owner data, UI integration, activation or configuration repair. The new draft PR targets the Phase 1 branch; PR #9 remains unchanged. Neither Stage 1 nor its tests revise M3/Phase 1 acceptance or remove the Planner end date.
2. Define the authoritative adapter from saved planned/actual/line-item modes and manual records to exact dated events. Preserve original IDs, amounts, validations, notes, marker, audits, original openings and anchor/cadence. Do not route unknown accounts to aggregate chequing. Pin source/entry/account/bucket revisions and an exact original reference manifest; no blanket rekey, account-ID mapping or historical Property Taxes corrections.
3. Establish posted bank openings and reserve ownership, explicit unallocated cash, pending carry decisions, already-in-opening exceptions, actual posting dates and identity representation decisions with owner-local evidence. Unknown/partial cases block, not forced adjustments. Detect and disposition overlapping manual/scheduled records before converting to events. Source schedule edits must be prospective; caller must reject stale/ambiguous source revisions.
4. Integrate Accounts, Planner, Dashboard, Transactions, Reports, budget/savings summaries and alerts through one scoped ledger contract. Keep projections distinct from actual/validated cash. Split reports crossing T, qualify legacy reports and preserve read-only legacy context; opening is not income and buckets are not extra assets. Stage 1 monthly report maps omit event kinds with zero activity; consumers must not treat a missing legacy period as verified zero.
5. Propose persisted checkpoint/association/legacy-context/audit capability and version policy separately. Stage 1 contractVersion is not a database schema. Do not assume unchanged old readers can ignore checkpoint semantics. Preserve legacy JSON and aliases; checkpoint-aware backups must serialize every required field, reject unsupported older readers and map exactly to future desktop storage. No schema/version number is assigned here.
6. Build an immutable preview/confirmation workflow with bounded exact membership and full before/after financial impact. Commit in one atomic IndexedDB transaction with re-read dependency/content guards and financial epoch. Abort on other-tab changes/import/deletion, quota or any write failure. No network/file work inside that transaction. Preserve complete prior audit and consent; no partial activation. Old app/service-worker writers must be blocked or reloaded.
7. Recovery must use audited compensating policy/reconciliation events; never delete raw history or erase later edits by restoring an old backup as ordinary undo. Reversal after dependent activity requires a fresh preview and matching revisions. Test crash/quota rollback, stale tabs, import conflicts, older-reader rejection, full restore and offline/PWA reopening. These storage/browser acceptance checks cannot be established by a pure Stage 1 engine.
8. Perpetual planning remains Continuous Planner Phase 2: bounded rolling/year windows, original date keys and cadence, recurrence evaluation between baseline and visible window, caches with revision invalidation and no persisted projected transactions. Stage 1 handles supplied dates through 2028 and beyond without a year reset, but provides no recurrence generator or year navigation. Calendar range is JS ISO four-digit dates, not an arbitrary fixed product end year.

## Architect F1/F2/F3 remediation

- F1 adds `account_transfer` for C→C, S→S and either cross-type direction, with two exact opposite bank legs, no bucket mutation and separate report movement totals. Self/unknown routes, extraneous bucket fields and insufficient available cash reject. Both tracks are independently funded; a validated transfer cannot spend forecast-only cash. Coincident scheduled/manual neutral transfers use the same explicit representation guard.
- F2 makes scheduled `origin.id` the stable source ID and `origin.occurrenceId` the mandatory original `sourceId__assignedDate` key. Multiple occurrences of one source, including source revisions/year boundaries, retain source and occurrence IDs. Duplicate occurrences reject regardless of changed event ID, revision or posting date; manual and adjustment records retain record-kind-specific identity. Existing Stage 1 synthetic fixtures now explicitly supply scheduled occurrence keys; no production data or adapter migration exists. Stage 2 must map existing original keys, not regenerate them or derive them from accounting dates.
- F3 rejects checkpoint dates earlier than originalAnchor before checking cadence modulo. Original anchor and valid later boundaries still pass; no backward Planner generator or pre-anchor policy is introduced.
