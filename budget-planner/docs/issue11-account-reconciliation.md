# Issue #11: account configuration prevention and historical reconciliation proposal

Status: preventative implementation plus design only for historical repair. Review baseline `5bba7dc178ed7da5f44b41f4473a02a6a6d4ba44`; final candidate SHA and validation are in draft PR #9. Issue #11's owner authorization permits Stage 1 and a Stage 2 proposal, not historical group writes, data repair, merge, deployment or Continuous Planner Phase 2. Independent Architect review and owner-private M3 remain open.

## Findings and implemented prevention

`SavingsBuckets.createNewBucket` assigned the literal demo savings ID. No account selector existed. `saveSavingsBucket` previously normalized and stored that ID without checking accounts; normalization/import preserve links rather than proving them correct. A custom account collection could therefore get a broken link on *new* bucket creation. This is a confirmed code defect, not proof of any particular historical mapping or account deletion.

New buckets now use actual active savings accounts. Exactly one is preselected; multiple require explicit selection; none show a create-account requirement and cannot pass validation. Both the form and the database command validate the chosen account. The database rereads accounts in the same transaction as the bucket write, so deletion, inactivity or type change before commit rejects a new bucket. Duplicate create submissions and stale/deleted existing bucket edits reject using the full saved bucket revision captured when the form opens. Failed saves keep the form open with an actionable error.

Existing associations are **read-only** on the bucket projection and editor. Display includes name/ID or missing link, wrong account type or inactive state. Opening/cancelling does not write. Ordinary edits retain the exact stored link, even if broken/inactive; changing any existing link is blocked at storage. This is the issue's read-only-plus-separate-repair option: a future reviewed configuration repair is needed to change existing associations. No repair button or historical mapping command is included. Existing bucket amounts and active state are not reset merely by opening/saving an editor.

Scheduled Items used a name-based `Main Chequing` default, not the literal demo account ID. That is insufficient evidence of the cause of the reported old demo chequing references. New defaults now use a sole actual active **chequing** account; ambiguous/absent defaults require choice. Existing blank or missing references are not replaced when the editor opens. New records and explicit account/type changes validate against current active accounts in the same transaction as source/snapshot writes. Legacy unchanged links are retained on unrelated source edits; existing UI validation can require resolving invalid required accounts before saving. Source-edit snapshot preservation stays unchanged; invalid writes roll back the entire transaction. Historical F4 still accepts archived references as evidence-backed history, independently of active-account rules for new configuration.

No financial formula, required backup field, schema/store or version changes. ExportVersion 1, data/schema 2, IndexedDB 9 and review app version remain unchanged. No owner backup, browser profile or financial database was accessed. Original backups are untouched.

## What is known about the legacy problem

Issue #11 reports two live accounts, a broken demo bucket association, a different broken scheduled-transfer account reference, a repeated 22-entry historical group and a separate 25-entry orphan/unusable-source cohort. These are **owner-reported aggregate observations**, not independently inspected or reconciled data. Counts can overlap across diagnostic causes; do not sum them into a unique total or conclude that fixing two links fixes all entries. No real record keys, proposed target IDs, amounts or mappings can be approved from these aggregates.

A matching demo string proves the stored reference, not the intended real account. A transfer's account field may be optional/unused by current aggregate transfer math, while a historical income/expense account can affect account-type classification. A bucket linked-account change may affect reference status without changing the current aggregate bucket formula. Never equate a zero aggregate delta with proof of correct ownership or original intent.

## Proposed local read-only inventory (not implemented as a new repair tool)

Use the existing Data Health live-reference warnings and Increment A canonical-entry inventory as the starting point. Before authorizing any repair, produce a private, immutable manifest from a *copy* of the current export, preserving the original file/hash. Enumerate exact structured fields, not arbitrary matching strings:

| Record class | Exact identity and candidate field | Required treatment |
| --- | --- | --- |
| Savings bucket | `savingsBuckets[id].linkedAccountId` | Separate current-configuration decision; list starting amount, linked activity and all dependent historical bucket references |
| Current schedule | `scheduledItems[id].accountId` (and any supported transfer endpoint fields separately) | Separate future-source decision; show cadence/date limits and saved entries with and without snapshots |
| Saved occurrence | `plannerEntries[entryKey].scheduledItemSnapshot.accountId`, bucket ID/alias and bucket-linked account dependencies | Historical classification decision, with key/source/date agreement and exact prior audit; F4 per entry where possible |
| Saved occurrence without snapshot | Exact saved key/source/date; fallback classification if current source exists | No inference of original account from present schedule; explicit evidence needed before F4 snapshot materialization |
| Orphan/unusable source | Exact key, any retained snapshot, absent source/type and identity issues | Separate unresolved queue, never manufacture a schedule/period or enroll automatically in account mapping |
| Other consumers | Explicit account fields in transfers, adjustments, budget/config records as supported | Report dependencies and conflicts; exclude from the proposed repair unless separately authorized |
| Prior evidence/audit | Previous/corrected tuples and evidence in `historicalSourceCorrections` and review metadata | Historical record of what was known; **never replace old IDs inside audit history** |

Read canonical `plannerEntries` and verify backup `planner.entries` alias agreement. Conflicting aliases, keys, dates, types or audit containers are blocking exceptions, not merge candidates. List stable ID, field path, exact before value, proposed after value, evidence reference/coverage, saved validation, active amount mode, overrides/line IDs, date window, source origin, prior correction count, revisions and dependency fingerprints. Include explicit excluded-record keys/reasons. Record unique entry counts and issue counts separately. Keep all details local; GitHub gets only redacted aggregates and synthetic examples.

For each **specific missing ID**, owner/Architect must establish a mapping with an original dated backup, account record or other corroborating evidence covering the original account/type and applicable dates. Bank statements alone may not establish internal bucket/category allocations. Same name, demo ID resemblance, current schedule, import success and `validated=true` do not establish historical equivalence. If account ownership changed over time, split evidence-covered periods; unknown boundary/contradictory evidence stays unresolved. Do not recreate a live account with a demo ID merely to silence diagnostics.

## Exact proposed writes and financial preview

Real-data write set: **none approved and none performed**. Stage 1 writes only explicitly saved configuration in synthetic tests. A later proposal must freeze exact member identities/fields and before/after records, never rerun a broad date query at commit or blanket-replace IDs. Separate three approval units: current bucket configuration, current recurring configuration, historical per-entry correction. Existing evidence-backed F4 is sufficient for accessible saved occurrences with known references and valid identities; preserve current/later schedules and correct each entry separately. It is impractical for large cohorts, but that does not authorize a batch shortcut.

Historical corrections must use F4's explicit entry-only confirmation/evidence and append-only `historicalSourceCorrections`. Preserve original `historicalReview.source` evidence in prior audit/context when superseding it; a future enhanced audit should explicitly retain the full preceding review object, reason, action kind, policy version, timestamp and immutable before/after revision. Existing F4 audits retain classification/provenance/evidence, but are **not a complete generalized undo journal**. No new audit format is implemented here. Do not revise old audit tuples to make them agree with a new account.

Before any future repair, run the shared Planner, bucket and Reports calculators against two **isolated in-memory copies** with only the frozen candidate changes applied. Include retained pre-anchor/off-screen dates, all affected downstream dates, projected and validated account-type totals, current/final bucket balances, report income/expenses/remaining balance and derived/manual transfer counts. FinPath currently exposes aggregate account-type math: do not claim bank-level per-account reconciliation from those totals. Check conservation where a correction reallocates between account types; do not assume every type/bucket correction conserves all reported subtotals. Show baseline/fallback limitations and unresolved orphan activity alongside numbers. Unreliable saved amounts or missing source facts block a complete reconciled-impact claim. Compare the full protected-field/ID/marker/audit manifest as well as totals.

## Missing schedules, concurrency and recovery design

A removed schedule with a usable snapshot is legitimate history and can retain its stable source ID. Missing schedule plus no usable snapshot remains a distinct unresolved cohort; do not fabricate recurrence to make it reachable. Existing F4 can operate on accessible saved cells; inaccessible orphan/identity cases need a separately designed, reviewed single-entry navigation/recovery path. Do not merge the 25 reported orphans into the 22-entry reference group or assume account mapping restores representation.

A future repair preview must capture exact entries, affected source/bucket records, references, account types/starting balances, source cadence, settings, adjustments/transfers, provenance and audit revisions used for impact calculations. Commit rereads them in one bounded IndexedDB readwrite transaction and rejects any mismatch, deletion, new member, import or unsupported shape. Full content fingerprints are preferable to timestamps alone. No broad re-query enrollment. No network/file reads or long asynchronous hash work within the transaction. A bucket/source repair changing fallback history must include those saved entries and downstream totals in its preview. Broadcast refresh after commit is helpful, but commit checks are authoritative. Retry is either idempotent with a matching operation ID or stale-rejected, not a duplicate audit append.

Recovery before any approved correction: keep untouched original and pre-change current JSON exports privately, verify fresh-profile restore, retain version/hash/manifest and ensure no concurrent writers. Do not overwrite original backups or use full restoration as an ordinary correction workflow. A future repair transaction must atomically append audit and commit exact changes; injected first/middle/final-write or quota failures roll everything back. Stage 1 bucket transaction failures already roll back with no partial writes.

After a committed repair, verify counts/values/IDs/markers/audits and shared calculator deltas against the frozen plan, export a distinct new backup and retain prior exports. Prefer an explicit evidence-backed compensating correction to undo one change, with a new audit event. Require the corrected record and dependent context still match expected revisions; otherwise stop for fresh review. Never delete intervening audit or revert unrelated later financial activity. Catastrophic full restore remains an owner-controlled emergency action after preserving the current dataset and explaining the loss of later edits. General batch rollback/undo is **proposal only**, requiring separate architecture and owner approval.
